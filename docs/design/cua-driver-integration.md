# Cua Driver integration

This integration is optional and experimental. Tisplay installs the MIT-licensed [Cua Driver](https://github.com/trycua/cua) v0.28.2 only after `tisplay cua install`. The installer selects Linux x86_64 or ARM64 and checks the archive against the SHA-256 published on the [upstream release](https://github.com/trycua/cua/releases/tag/cua-driver-rs-v0.28.2). It adds no Python dependency to ordinary Tisplay viewing.

Use `tisplay cua tools` and `tisplay cua describe TOOL` to inspect the pinned driver's live tool registry and schemas. `tisplay cua call --session ID TOOL --args JSON` invokes a tool. For Linux, `get_window_state` returns a structured AT-SPI element tree and snapshot-scoped element tokens; pass `element_token` and `snapshot_id` to a later semantic action such as `click`. Tisplay injects a stable Cua `session` argument when the live schema supports it. `--out FILE` stores returned image data on the machine running the Tisplay CLI, and normal output removes embedded image bytes and duplicate Markdown tree text. Use `--raw` only when the full driver response is needed.

Each Tisplay session owns one Cua Driver process, private Unix socket, and log under that user's runtime directory. Separate `cua call` processes connect to the same socket so Cua snapshot references can be reused. `session stop` terminates only its tracked Cua process group and removes its owned runtime files. `tisplay cua mcp --session ID` exposes the upstream MCP server through stdin/stdout; remote use remains `ssh -T` stdio with no remote TCP listener. Both process and CLI calls set `CUA_DRIVER_RS_TELEMETRY_ENABLED=false` and `CUA_DRIVER_RS_UPDATE_CHECK=false`. Tool calls hold and renew the Tisplay input lease while running.

The integration was verified in an isolated Linux X11 environment: separate Tisplay CLI calls listed a Zenity window, read its AT-SPI tree, clicked the returned text-field token, typed a marker, then clicked the refreshed OK-button token. Zenity exited with the exact expected marker, and stopping the Tisplay session removed the Cua socket. The Pi smoke verified Cua on X11; its labwc native session currently lacks `at-spi2-core` and does not expose an XWayland window list, so native labwc semantic actions are **not verified**. On Debian-derived hosts, install `at-spi2-core` and `libxi6` when required by the Cua Linux runtime. `cua doctor --session ID` reports the selected backend and live prerequisites. The upstream [platform guidance](https://cua.ai/docs/reference/cua-driver/platform-support) is compositor-specific; do not infer labwc support from X11 results.

Tisplay's screenshot API also returns a one-use `capture_id` for precise pixel actions. Supply it to `click`, `move`, `drag`, or `scroll` after a cropped or scaled Tisplay screenshot; those coordinates are interpreted in that screenshot's pixel space. Cua element tokens and Tisplay capture IDs are separate mechanisms and are not interchangeable.

Related upstream references: [CLI](https://cua.ai/docs/reference/cua-driver/cli-reference), [Linux tools](https://cua.ai/docs/reference/cua-driver/mcp-tools-linux), [telemetry settings](https://cua.ai/docs/reference/cua-driver/telemetry).
